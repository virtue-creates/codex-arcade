# Game Design Intent Report

このテンプレートは、各 `Cabinet Studio` が本部へ返す「ゲーム性の意図レポート」。

`Cabinet Studio` は、各Cabinetゲームを担当する制作チーム/チャットの呼び方。

例:

- Cabinet 01 Studio: `neon-core-survivor`
- Cabinet 02 Studio: `metro-mender`
- Cabinet 03 Studio: `specimen-night-shift`

目的は、完成報告を単なる「動きました」にしないこと。

本部と人間QAは、このレポートを見てから実際に遊び、以下を判断する。

- 開発者が狙った楽しさは伝わっているか
- 人間が感じた楽しさ/分かりづらさと、開発意図がズレていないか
- 改善すべき点がバグなのか、説明不足なのか、ゲーム設計そのものなのか

## いつ提出するか

Cabinet Studioは、以下のタイミングで提出する。

1. MVP実装完了時
2. 大きなゲーム性変更の前
3. QA後の改善版を出す時

## 提出フォーマット

```md
# Game Design Intent Report: [Game Title]

## 1. このゲームは何をするゲームか

概要を書く。

プレイヤーが1プレイ中に何を見て、何を操作し、何を目指すゲームなのか。

ここでは細かいルールよりも、ゲームの全体像が分かることを優先する。

## 2. ルール

実際に遊ぶ時のルールを書く。

最低限、以下を分けて説明する。

- 開始条件
- プレイヤーができる操作
- できること/できないこと
- スコアが増える条件
- ミス、失敗、ペナルティ
- クリア条件
- ゲームオーバー/終了条件
- 1プレイの長さ

## 3. 初見プレイヤーに何が伝われば成功か

最初の30秒で分かってほしいこと。

例:
- 何を操作すればよいか
- 何を目指せばよいか
- 成功/失敗の違い
- 少し難しそうだが、もう一回やれば分かりそうという感覚

ここは本部と人間QAにとって特に重要。

細かいルールの正確さだけでなく、初見プレイヤーが「なんか分かる」「むずいけど楽しいかも」と感じられるかを見る。

## 4. プレイヤーにとって何が楽しい想定か

例:
- 反射神経が気持ちいい
- ルートを考えるのが楽しい
- うまく誘導できた時に気持ちいい
- スコア更新を狙いたくなる
- 見た目や演出を触っているだけで楽しい

## 5. どこで悩ませるゲームか

プレイヤーに選択や判断がある場合、何を迷わせたいのか。

例:
- どの区間を先に直すか
- どの敵を避けるか倒すか
- どのピンをどこに置くか

## 6. どこで気持ちよくさせるゲームか

成功した瞬間、連鎖した瞬間、スコアが伸びた瞬間など、体験の山場。

## 7. 今回のMVPで意図的に捨てたもの

時間やスコープの都合で入れていない要素。

## 8. 現時点で開発者が不安に思っていること

遊び方が伝わるか、単調すぎないか、難しすぎないか、操作が分かるか、など。

## 9. 確認事項の仕分け

本部や人間プレイヤーに確認してほしいポイントを、以下に分ける。

```md
### AI間確認

本部や他部署で処理してよい確認事項。

例:
- ファイルの場所
- manifest更新
- QA手順
- 実装範囲

### 人間ディレクター判断

人間の感覚、好み、公開判断が必要な事項。

例:
- 面白いか
- 世界観としてアリか
- 公開してよいか
- 看板筐体として扱ってよいか

### 共有のみ

返答不要の報告事項。

例:
- 実装したこと
- 確認済みのこと
- 未対応のこと
```

今後、本部はこの仕分けを見て、人間ディレクターに聞くべきことだけを出す。
```

## 本部での使い方

本部は、提出された意図レポートと人間QAの感想を照合する。

照合の見方:

- 意図どおり伝わっていて楽しい: 磨き込みへ進む
- ルールは良いが伝わっていない: UI/説明/演出を改善する
- 意図自体が弱い: ゲーム性を再設計する
- 想定外に別の楽しさがある: 方向転換を検討する

このレポートは、将来の自動QAやエージェント分業でも使う。
